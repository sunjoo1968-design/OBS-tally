# v1.5.10 OBS 방송 안정성 검토

점검/검증: 2026-09-17. 현재 Hub에 포함된 OBS WebSocket 안정성 패치를 정리한 문서입니다.
이번 리스너 업데이트에서는 검증된 OBS/vMix 핵심 로직을 추가 변경하지 않았습니다.

## 문제와 적용한 조치

| 문제 | 현재 처리 |
| --- | --- |
| 컬렉션 교체 중 장면·그룹·출력 요청 | Changing~Changed 동안 모든 새 요청 중지, 진행 중 응답 무효화 |
| 종료/믹서 변경 후 늦은 연결과 재접속 | 정지 플래그, 클라이언트 식별, 타이머 취소, 재연결마다 새 소켓 |
| 무응답 연결/요청의 무기한 대기 | 연결 8초, 요청 5초, 비중첩 생존 확인 5초, 실패 시 상태 해제 |
| 이벤트마다 전체 장면 병렬 조회/불완전 캐시 | 50ms 병합, 단일 갱신, 순차 장면·그룹 조회, 공유 장면 캐시, 완성된 스냅샷 게시 |
| 오래된 응답이 최신 PGM/PVW/출력 덮어쓰기 | 항목별 revision 및 컬렉션 epoch 확인 |
| 그룹 오판 및 녹화 일시정지 오류 | v5 isGroup/그룹 전용 요청, PAUSED 상태 반영 |
| 저장 경합/자동 저장 오류로 Hub 종료 | 직렬화·임시 파일 fsync·rename, 예약 저장 실패 처리, 기존 파일 보호 |

공식 OBS 프로토콜은 컬렉션 교체 중 요청의 동작을 보장하지 않으며 크래시 가능성을 경고합니다.
Hub는 해당 이벤트 구간의 새 요청을 차단합니다. 이미 보낸 요청을 OBS에서 취소하지는 못하며 응답을 폐기합니다.
[OBS 공식 프로토콜](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#currentscenecollectionchanging)

## 부하와 복구

- 일반 PGM/PVW 이벤트는 캐시로 처리하여 전체 목록을 조회하지 않습니다.
- 구조 이벤트는 50ms 병합, 조회 중 변경은 후속 갱신으로 처리합니다.
- 장면·그룹 요청은 순차 진행하고 공유 하위 장면을 한 번씩 조회합니다.
- 생존 확인은 GetCurrentProgramScene 한 건이며 완료 후 다음 5초를 예약합니다.
- 장면 조회 실패는 1초 후 재시도, 연속 3회 실패 시 오래된 탈리를 해제하고 재연결합니다.
- 재연결 backoff는 1/2/4/8/10초입니다. 정상 스냅샷/생존 확인 후 초기화합니다.
- 기본 always 모드는 GetStreamStatus/GetRecordStatus를 호출하지 않습니다.
- stream/record/streamOrRecord는 초기 연결 및 컬렉션 교체 후 필요한 출력 상태를 조회합니다.

## 검증

Hub 25 suites, 250 tests 통과(기존 null 설정 1개 제외). OBS 관련 39 tests 중
실제 WebSocket 전송 검사는 4개입니다. TypeScript/React/Windows pkg/.NET 빌드 성공.
현재 실행 파일 버전은 1.5.10이며, 다음 패키지 smoke 5개가 모두 통과했습니다.

1. HTTP V1.5.10/제작자 표기, 펌웨어 3종 준비, OBS v5 소스 탈리
2. 500개 이벤트를 조회 한 번으로 병합하고 소스 비활성화 반영
3. 컬렉션 교체 중 요청 중지 및 완료 후 복원
4. 강제 소켓 단절 시 상태 초기화와 자동 재연결
5. 채널 다중 지정 저장 및 프로세스 재시작 후 매칭 모드 복원

Jest 경로는 JSON, Windows pkg 경로는 MessagePack을 사용하여 두 형식을 검증했습니다.
검사는 임시 설정/포트에서 실행했고 실제 사용자의 설정을 사용하지 않았습니다.

## 제한과 실무 확인

실제 OBS 인코더/FFmpeg/캡처 드라이버/플러그인 조합의 장시간 송출은 자동 검사 범위가 아닙니다.
이전에 제시한 크래시 파일은 현재 경로에 없어 새 패치와 직접 대조하지 못했습니다.
OBS 자체 크래시가 완전히 해결되었다고 단정하지 않습니다.

방송 외 시간에 일반/그룹/중첩 장면의 PGM/PVW, 컬렉션 교체, OBS 재시작,
네트워크 단절, 녹화 일시정지/재개, 채널 복원을 실제 환경에서 확인합니다.
인코더 리허설 후 OBS/Windows 로그도 확인합니다.

요청 응답이 5초 이상 지연되면 연결을 재설정합니다. 컬렉션 변경 완료 이벤트가
오지 않으면 요청을 재개하지 않습니다. 자동 저장은 500ms 병합 구간이 있으므로
변경 직후 강제 종료까지의 미저장 가능성은 남습니다. fsync/rename은 디스크 자체 장애를 보장하지 않습니다.

기존 의존성 audit에는 개발 도구를 포함한 취약점 219건이 보고되었습니다.
강제 메이저 업그레이드는 방송 안정성 패치와 분리했습니다. NuGet 취약성 조회 실패(NU1900),
WebRequest 경고(SYSLIB0014), 오래된 Browserslist/Node API 경고도 남습니다.
전체 의존성 보안 점검 완료를 뜻하지 않습니다. 신뢰할 수 있는 LAN에서만 사용하고 OBS 인증을 켭니다.
